# Licensing transport boundary

The C++ adapter in `src/rds/license_transport.*` converts explicitly selected licensing-message buffers to and from the transport envelope expected by IronRDP. It is **framing code only**: no licensing engine, COM license object, service connection, or session is implemented by this component. The bridge still returns its existing licensing error until a real backend is integrated.

## Implemented contract

- `wrapServerMessage` adds a TPKT/X.224/MCS SendDataIndication envelope. The caller selects either a licensing preamble or a Basic Security Header followed by that preamble.
- `unwrapClientMessage` accepts one complete SendDataRequest, checks the expected initiator and channel, and returns the selected buffer representation.
- Both directions enforce exact outer/inner lengths, known message types, direction, protocol versions 2/3, and the extended-error flag. Errors clear the output. Error-alert contents are preserved, not interpreted as permission.
- The supported envelope has an unencrypted Basic Security Header with `SEC_LICENSE_PKT`, one unsegmented MCS message and no trailing packet. Encrypted outer security headers and fragmented MCS encoding are rejected. The licensing payload's own encrypted fields remain untouched.
- The maximum message is 16,371 bytes, leaving room for the Basic Security Header and MCS fields within the protocol's 16,383-byte MCS limit. There are no file, registry, network, service or trace operations.

A successful framing result does **not** validate the message body, server certificate, license, MAC, licensing state, or account. Those checks belong to the genuine client implementation and the Windows service. [Licensing PDU](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpele/dfeaae30-7fa2-48a1-abc6-8c027e413c16), [preamble](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpbcgr/73170ca2-5f82-4a2d-9d1b-b439f3d8dadc), [MCS size limit](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpbcgr/b61e1c76-5d7c-4285-b61a-b69f85e4a0e2).

## Service-buffer interpretation remains to be observed

Microsoft's COM documentation references the named MS-RDPELE request/response structures. Their definitions and examples begin with `LICENSE_PREAMBLE`, which supports choosing `BufferFormat::Preamble`. However, the COM pages do not explicitly identify a byte offset. The adapter deliberately does not guess or strip bytes on failure. Before enabling a backend, a controlled service call must confirm the selected format using bounded metadata only; raw identity, certificate, encrypted license or key buffers must not enter public logs. [SendClientLicense](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nf-wtsprotocol-iwrdsprotocollicenseconnection-sendclientlicense), [server-message example](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpele/a870d76a-639b-4757-9370-a9bdfbfd6961).

`RequestClientLicense` receives a caller-owned output buffer (`PBYTE`, not `PBYTE*`) and an in/out byte count. Its `Reserve1/Reserve2` inputs are documented as additional client data, not as necessarily unused. A future bridge must reject an unsupported nonempty additional-data contract rather than silently discard it. An undersized output must retain the pending client reply and report the required size; it must not execute the licensing step twice. [RequestClientLicense](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nf-wtsprotocol-iwrdsprotocollicenseconnection-requestclientlicense).

## Concrete optional backend design

The investigated upstream revision is **`3c778f779a4df7c0fe67a450f55498a99c80da95`** of **Devolutions/IronRDP**, licensed **MIT OR Apache-2.0**. Its connector package declares Rust 1.94. No Rust compiler was found in PATH or the specifically checked local tool directories; no toolchain was installed. This repository currently includes no copied IronRDP source or linked IronRDP binary. Credit is for the protocol/client research, not a claim of completed integration. [Pinned license exchange](https://github.com/Devolutions/IronRDP/blob/3c778f779a4df7c0fe67a450f55498a99c80da95/crates/ironrdp-connector/src/license_exchange.rs), [package](https://github.com/Devolutions/IronRDP/blob/3c778f779a4df7c0fe67a450f55498a99c80da95/crates/ironrdp-connector/Cargo.toml), [license declaration](https://github.com/Devolutions/IronRDP/blob/3c778f779a4df7c0fe67a450f55498a99c80da95/Cargo.toml).

The next backend can use a pinned Rust `cdylib` with three C ABI operations: create a per-connection context, process one fully framed input into an owned output, and destroy the context. The C++ owner must serialize calls and copy an output before the next step. A versioned creation structure would provide the username, optional domain, stable per-client hardware identity, route and cache callbacks. It must not contain or log a password.

The Rust context would own `LicenseExchangeSequence` and its cryptographic state. It should use the upstream cryptographic random generator, implement `LicenseCache` with real per-client storage and propagate storage failures. A no-op store must not be presented as a persistent cache. Any incorporated source or redistributed dependency must retain the selected upstream license and notices. The FFI must catch panics, bound lengths and produce static error codes rather than dumping decoded packets.

`Sequence::step` consumes an X.224-wrapped MCS SendDataIndication and produces an actual SendDataRequest reply or no reply. The adapter checks routing independently. Incoming server errors remain errors. Upstream handles an actual server `STATUS_VALID_CLIENT`; the bridge must never fabricate one to finish the exchange. Cache reuse, RSA response, challenge verification and new-license storage need tests against real upstream code before integration. [Pinned MCS codec](https://github.com/Devolutions/IronRDP/blob/3c778f779a4df7c0fe67a450f55498a99c80da95/crates/ironrdp-pdu/src/mcs.rs).

Client capabilities must describe the implemented algorithm, certificate handling, version and client identity. Do not claim server authentication merely because the client parses a certificate. Only Windows' `ProtocolComplete` argument records the service's licensing decision: exactly 1 means success; other values mean failure. Client state completion, a valid frame or an empty output cannot substitute for that notification. [Capabilities](https://learn.microsoft.com/en-us/windows/win32/api/wtsdefs/ns-wtsdefs-wts_license_capabilities), [ProtocolComplete](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nf-wtsprotocol-iwrdsprotocollicenseconnection-protocolcomplete).

## Verification

The standalone C++17 harness passed **129 offline checks** with MSVC warnings treated as errors. It checks a fixed negative licensing-message fixture, all truncated prefixes, routing and direction mismatches, length boundaries, unsupported security/segmentation, output clearing and input/output aliasing. Boundary payloads are explicitly opaque framing fixtures. No cryptographic interoperability, real server licensing, Windows session or physical-seat behavior is claimed.
