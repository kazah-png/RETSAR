# Minimum integration for a legitimate RDS laboratory session

**The current bridge cannot create a supported first session.** Its `GetLicenseConnection` returns `E_NOTIMPL`; Microsoft explicitly specifies that an error from this method makes RDS drop the connection. Returning a successful empty license object would conceal the missing implementation rather than supply it. [GetLicenseConnection](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nf-wtsprotocol-iwrdsprotocolconnection-getlicenseconnection)

The official connection diagram places the licensing handshake before **New session created**, followed by `NotifySessionId`, input/video setup and eventually `LogonNotify`. Therefore omitting a valid licensing implementation cannot be justified as a way to test an earlier session-creation stage. [Connection sequence and diagram](https://learn.microsoft.com/en-us/windows/win32/termserv/connection-sequence)

Service activation and listener startup are now [verified in the disposable Server guest](ACTIVATION-TRACE.md#verified-service-activation-after-the-dll-permission-correction): 21 decoded RETSAR events came from TermService, with successful manager initialization, listener creation and `StartListen`. `Listener.GetSettings=E_NOTIMPL` did not prevent startup; a later service-state notification also returned `E_NOTIMPL`. A later authenticated [service-control experiment](SERVICE-CONTROL.md) requested one real connection and received `E_INVALIDARG` before a connection callback or session was returned. `Initialize` accepts the optional null `IWRdsProtocolSettings` pointer, retains it only when present, and rejects a null required `WRDS_SETTINGS` pointer, but still does not validate or consume the supplied settings structure. Settings and notification contracts remain incomplete; observed listener activation does not imply that the connection or licensing sequence will succeed. The manager has no `GetDefaultSettings` or `GetProtocolSettings` methods: the separate service-supplied `IWRdsProtocolSettings` exposes `GetSettings` and `MergeSettings`. [Manager contract](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nn-wtsprotocol-iwrdsprotocolmanager), [Settings interface](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nn-wtsprotocol-iwrdsprotocolsettings), [Listener settings](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nf-wtsprotocol-iwrdsprotocollistener-getsettings)

## What the contracts require

| Area | Documented requirement | Remaining integration |
| --- | --- | --- |
| Service instance | RDS instantiates the registered manager and supplies a callback to its listener. | Reach that exact listener from an authenticated controller; a separate test-process manager is unrelated. |
| Settings | `Initialize` supplies service settings; `GetSettings` and `GetClientData` return actual listener/client settings. An error from `GetClientData` drops the connection. | Consume and preserve applicable service policy, supply meaningful data, and validate settings with the real service. Zero-initialized mock settings are not evidence of inherited security defaults. |
| Credentials | Successful `GetUserCredentials` passes the supplied user name, domain and plaintext password to WinLogon. An error or incorrect credentials causes the normal logon UI. | Either provide a functioning display/input path for that UI or securely supply credentials for a dedicated laboratory account, with transient memory and no credential logging. |
| Authorization | `IsUserAllowedToLogon` receives an authenticated user token for the provider's decision. | Check the expected laboratory principal and admission policy; do not replace the current error with an unconditional success. Preserve Windows authentication and logon policy. |
| Licensing | `GetLicenseConnection` returns a referenced, operational `IWRdsProtocolLicenseConnection`. | Implement a genuine client licensing exchange and let RDS determine its outcome. |
| Reconnection | `AuthenticateClientToSession` may return an error to continue the ordinary sequence. `SessionArbitrationEnumeration=E_NOTIMPL` selects normal arbitration. | Keep these defaults; use a separate test account and record whether RDS created or reused a session. Never claim a new session solely from a numeric ID. |
| Graphics and input | The provider supplies its device/graphics path. `GetInputHandles` describes keyboard/mouse device handles, not a successful null-handle shortcut. | Implement and validate the real transport and supported remote graphics integration before claiming a usable session. |

Sources: [Initialize](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nf-wtsprotocol-iwrdsprotocolmanager-initialize), [GetClientData](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nf-wtsprotocol-iwrdsprotocolconnection-getclientdata), [GetUserCredentials](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nf-wtsprotocol-iwrdsprotocolconnection-getusercredentials), [IsUserAllowedToLogon](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nf-wtsprotocol-iwrdsprotocolconnection-isuserallowedtologon), [AuthenticateClientToSession](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nf-wtsprotocol-iwrdsprotocolconnection-authenticateclienttosession), [SessionArbitrationEnumeration](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nf-wtsprotocol-iwrdsprotocolconnection-sessionarbitrationenumeration), [GetInputHandles](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nf-wtsprotocol-iwrdsprotocolconnection-getinputhandles).

## Licensing is an exchange, not a Boolean

The minimum licensing object must return real client capabilities, relay `SendClientLicense` packets to a genuine client implementation, return the client's actual replies through `RequestClientLicense`, and record the outcome supplied by `ProtocolComplete`. The packet contract is [MS-RDPELE](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rdpele/3d3f160a-3ab3-4dfb-ba4e-47c27cd79409). Capability fields must describe implemented behavior; protocol success is decided by the service, not asserted by the bridge. Service notifications must not reenter RDS. [License interface](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nn-wtsprotocol-iwrdsprotocollicenseconnection), [RequestClientLicense](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nf-wtsprotocol-iwrdsprotocollicenseconnection-requestclientlicense), [ProtocolComplete](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nf-wtsprotocol-iwrdsprotocollicenseconnection-protocolcomplete)

Microsoft's sample explicitly leaves that implementation unfinished. Its placeholder successful methods are not a usable licensing transport and are not adopted here. Installing the RDSH role or using a server evaluation does not implement this provider contract. [Sample licensing source at the investigated revision](https://github.com/Azure/Remote-Desktop-Services-Protocol-Sample/blob/0b5a0bae1cc1c2a667b5962bd7847d5181ae375f/Sample/TestProtocol_Ext/WRdsProtocolLicenseConnection.cpp)

## Service-side trigger and registration scope

The [implemented guest control channel](SERVICE-CONTROL.md) reaches the service-created listener. Its authenticated local pipe queues metadata-only Start, Continue, Cancel and Snapshot commands to a separate MTA worker. StartListen itself never requests a connection. The real guest experiment reached OnConnected and observed a rejection; a different manually created manager remains unrelated to that listener.

The pipe has an explicit SYSTEM/elevated-administrator DACL, remote-client rejection, a first-instance reservation, fixed messages, token validation and verified impersonation reversion before dispatch. StopListen revokes admission without waiting for outbound RDS callbacks. Fixed leases bound admission and cooperative cleanup; they cannot forcibly interrupt a blocked RDS call. The observed HRESULT is retained instead of treating endpoint availability as session creation.

Registration belongs only inside an explicitly prepared disposable guest: the project CLSID's `InprocServer32` points to the guest DLL with `ThreadingModel=Free`; a separate `WinStations` listener names that CLSID in `LoadableProtocol_Object`. The standard `RDP-Tcp` listener and other providers remain untouched. RDS discovers the provider when its service starts. None of this registers a component on the everyday host. [COM registration](https://learn.microsoft.com/en-us/windows/win32/com/inprocserver32), [RDS registration](https://learn.microsoft.com/en-us/windows/win32/termserv/registering-the-custom-protocol), [Start sequence](https://learn.microsoft.com/en-us/windows/win32/termserv/start-sequence)

## Can IDD and input be postponed?

**For an activation/error-path test, yes; for a promised usable session, no.** The current implementation has reached a real service-supplied listening callback. The protected service trigger is implemented and observed; the first OnConnected attempt was rejected before licensing. Remaining connection and licensing contracts still need implementation and validation. Listener activation and any subsequent rejection must remain distinct from session creation.

After implementing a legitimate licensing exchange, the documented ordering makes an allocation-only experiment plausible: observe `NotifySessionId` before the missing device methods fail, then record the actual cleanup outcome. This is an inference about a bounded experiment, not a guarantee that a server build will leave a usable session. There is no verified supported headless fallback here. The ordinary logon-screen fallback cannot be operated without working graphics and input. The documented `GetVideoHandle=E_NOTIMPL` exception requires another implemented graphics path; it is not blanket permission to omit graphics. [GetVideoHandle](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nf-wtsprotocol-iwrdsprotocolconnection-getvideohandle)

Remote IDD integration additionally requires the OS remote desktop stack to create the relevant device; merely assigning a session number to a virtual monitor does not meet the contract. [Remote IDD requirements](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/iddcx1.4-updates-for-remote-idds)

Windows Server testing validates only that laboratory configuration. It does not establish concurrent physical seats on Windows 11 Home, remove Windows licensing requirements, or complete RETSAR's native-seat milestone.

## Lower-complexity research control

The standard Windows Remote Desktop Connection client and RDP listener offer a separate Server-only control experiment. Windows supplies their existing connection, authentication and licensing protocol implementations; RETSAR would observe a normally authorized session instead of implementing those protocols first. The server still makes normal access and licensing decisions, and its requirements remain applicable. [Remote Desktop Connection](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/mstsc), [RDS licensing model](https://learn.microsoft.com/en-us/windows-server/remote/remote-desktop-services/rds-client-access-license)

**Recommendation:** use that standard path only as an explicitly labelled laboratory reference for session identity, the probe, observation and recovery work. Keep the custom bridge available for activation/contract testing. Defer a new licensing client until a supported target configuration and a concrete need for a custom transport justify it. Implementing it now would add substantial protocol work without resolving Windows 11 Home concurrency or exclusive physical display/input binding.

This is an engineering prioritization inference, not a replacement for the requested native physical-seat application. A remote viewer, an RDP session and a VM desktop must not be relabelled as a completed independent physical seat or as P0 evidence. No standard-RDP backend is implemented by this document.

## Next decisive experiments

These remain guest-only experiments, not physical-seat capabilities. Service/listener activation and delivery of one authenticated request to that exact instance are now observed. The first request was rejected; identify the requested connection interfaces and the invalid contract before changing settings. Manual COM construction cannot substitute for the listener created by TermService.

1. **Exercise one real connection.** Use an authenticated local worker holding that listener's callback. Call `OnConnected`, then queue `OnReady` only after `GetLogonErrorRedirector` has arrived and the returned connection callback is available. Make outbound RDS calls on a separate worker thread to avoid callback reentrancy. Record the service PID, callback order and original HRESULTs; stop at the first unresolved contract. [OnConnected](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nf-wtsprotocol-iwrdsprotocollistenercallback-onconnected), [OnReady ordering](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nf-wtsprotocol-iwrdsprotocolconnectioncallback-onready), [callback threading](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nn-wtsprotocol-iwrdsprotocolconnection).

2. **Relay a genuine licensing exchange.** Investigate IronRDP's public `LicenseExchangeSequence` as a reusable MIT/Apache-2.0 client implementation. Its MCS framing needs an explicitly validated adapter to the MS-RDPELE buffers exchanged by RDS; suitability is an inference, not a tested integration. Pin the source revision before reuse, retain normal server decisions and record only the service-supplied `ProtocolComplete` outcome. Correlate subsequent session and Winlogon notifications with owned account/process identity and unchanged reference-session observations. Allocation followed by a device failure is not a usable seat. [IronRDP source](https://github.com/Devolutions/IronRDP/blob/master/crates/ironrdp-connector/src/license_exchange.rs), [project license](https://github.com/Devolutions/IronRDP), [buffer contract](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nf-wtsprotocol-iwrdsprotocollicenseconnection-requestclientlicense), [ProtocolComplete](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nf-wtsprotocol-iwrdsprotocollicenseconnection-protocolcomplete).

3. **Validate graphics and input separately.** A remote IDD must be instantiated by the OS remote stack for the candidate session, then produce an updating surface. `GetInputHandles` still needs real keyboard/mouse device handles; a null success, host `SendInput` or generic virtual HID is not proof of that contract. Compare candidate and reference observations simultaneously. Even successful remote image/input transport does not assign an independent physical display connector or keyboard/mouse. [Remote IDD prerequisites](https://learn.microsoft.com/en-us/windows-hardware/drivers/display/iddcx1.4-updates-for-remote-idds), [GetInputHandles](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nf-wtsprotocol-iwrdsprotocolconnection-getinputhandles).

The newer `IWRdsProtocolConnection2` lists Windows build 26100 as its minimum client and adds serialized credentials; it is unavailable on the 20348 laboratory target. That documentation does not establish simultaneous physical seats on Windows 11 Home. The original manager's support table and the sample's concurrency limits remain separate constraints. [Connection2](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nn-wtsprotocol-iwrdsprotocolconnection2), [manager requirements](https://learn.microsoft.com/en-us/windows/win32/api/wtsprotocol/nn-wtsprotocol-iwrdsprotocolmanager), [official sample](https://github.com/Azure/Remote-Desktop-Services-Protocol-Sample).
